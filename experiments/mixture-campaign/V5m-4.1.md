# V5m-4.1: Full-inventory, resumable mixture mission screening

## Scope

This revision changes orchestration, coverage diagnostics and controls. It reuses
V5m-4's mission profile, numerical driver, binary models, property limits and
content-addressed Store without changing those files. It is not a new reactive,
ablative, boundary-layer or porous-flow solver. It does not provide new empirical
references, train ML, certify hardware feasibility, or promote a production fluid.

The default is all locally eligible neutral C/H/O water/additive pairs, not a new
500-pair sample. The actual inventory size is reported rather than hardcoded.
The published prior inventory contained 6009 eligible pairs, but another database
or environment can produce a different population. This is still a bounded model
and chemical domain, not all liquids, solids, electrolytes or ternary mixtures.

The initial 40-composition grid and 900 K outlet ceiling are inherited unchanged.
Previously interesting compositions are also retained where they fit the current
scope. Exactly zero additive is a control, not another discovered formulation.
A low required mass remains conditional on the fixed heat-demand profile and the
unchanged nonreactive model assumptions.

## Commands

After installing this revision into the repository:

```bash
cd /home/user/DEV/autonomous-materials-lab
source experiments/entry-evaluator/.venv/bin/activate
python -m unittest discover -s experiments/entry-evaluator/tests -p 'test_mission_batches.py' -v
python -m unittest discover -s experiments/entry-evaluator/tests -p 'test_campaign*.py' -v
python -m unittest discover -s experiments/entry-evaluator/tests -p 'test_csv_publication.py' -v
cd experiments/mixture-campaign
python run_campaign.py
```

The default `mission-campaign-v41.yaml` sets `catalog.maximum_pairs: null`,
`continuation.batch_pairs: 50`, and `continuation.max_batches: null`. One invocation
continues automatically until the current inventory is screened. It publishes a
checkpoint snapshot after every batch and its current detailed studies.

```bash
python run_campaign.py --max-batches 1
python run_campaign.py --batch-pairs 25 --workers 4
python run_campaign.py --status
```

`--max-batches 1` is an invocation work budget, not a catalog filter. Running the
normal command afterwards continues pending work. The compatibility flag
`--limit-pairs N` means one batch of at most N pending pairs in this mode.
`--status` reads the latest committed publication pointer without constructing a
numerical driver. It need not wait for a running batch to finish.

`--retry-failures` retries failed tasks/studies. It does not magically fill a
model-domain gap returned as a successful task with an unsupported-state result.
`--recompute` bypasses compatible numerical and dossier caches deliberately.
Neither flag is needed after normal interruption. Keyboard interruption preserves
completed pair checkpoints and records an interrupted snapshot when possible.
A hard process kill may leave only pair checkpoints from the partial batch; those
are discovered on the next invocation. Atomic file replacement prevents a partial
JSON write from being treated as a completed result.

Old entry points remain available:

```bash
python run_campaign.py --mode mission-v4
python run_campaign.py --mode properties
```

No command installs packages, changes the thermodynamic environment, downloads
literature, runs a physical experiment, or automatically commits/pushes Git.

## Numerical cache migration

Do not delete `.campaign-cache` or old published results. V5m-4 task names, inputs,
Store ABI and backend implementation hashes remain unchanged. Existing positive-
composition model states can therefore be reused when their complete signatures
match. There is no blanket assertion that all old tasks are reusable under a
changed library environment, configuration or parameter set.

The first V5m-4.1 pass builds new dossiers and runs newly required zero-limit
controls. Old pairs are not marked complete merely because they appear in an old
ranking; they pass the current common suite, using matching old numerical states.
An architecture test explicitly verifies that a V5m-4 coarse cache is reused and
only zero-composition states need new calls for that unchanged coarse design.

Each pair/stage owns a short-lived Store, so raw state outcomes, graphs and event
lists do not accumulate across the full inventory. Numerical state memory scales
with active workers and the largest active pair/stage; metadata and compact
cumulative summaries still scale with the catalog. Finalist state replay remains
more expensive than the coarse screen. This is not a strict byte-level RAM cap.

## Persistence and publication

Results use a separate root:

```text
mission-v5m41-results/
    latest.json
    objects/<content-sha256>.json.gz
    run-<UTC>-<id>/
        summary.json
        summary.json.gz
        scientific-results.json.gz
        registry.json.gz
        manifest.json.gz
        report-pair-summary-*.csv.gz
        report-finalists-*.csv.gz
        report-failure-diagnosis-*.csv.gz
        report-zero-controls-*.csv.gz
        report-history-out-of-scope-*.csv.gz
        report-changes-*.csv.gz
        table-*.csv.gz
        preview-*.md
        publication-index.json
```

Objects are immutable and shared across snapshots. A dossier contains records,
zero controls, raw model responses, studies and its task graph. Its compressed
hash and uncompressed content hash are checked. Cumulative registry entries point
to the relevant dossiers rather than copying every raw state into every snapshot.
The catalog, fixed mission profile and shared task graph are also stored once as
content-addressed objects. Always publish the whole result root, including objects.

New CSV files are gzip only. Small Markdown previews are explicitly incomplete;
they are not the entire ranking. The scientific digest, registry digest, object
references and local-file hashes permit independent verification of publication.
The text connector is not assumed to decode gzip. No old result is overwritten,
and no Git history is rewritten.

Local stage pointers live under `.campaign-cache/mission-v41-pointers/`. They
include the complete protocol signature, object digest and dependency outcomes.
An upstream result that changes for the same task key invalidates its dependent
dossier. A corrupt hash is an error, not an invitation to silently substitute data.
Changing numerical implementation invalidates dependent states. Changing a study
rebuilds dossiers/studies but retains compatible numerical cache entries.

## Historical continuity

The configured old property and mission result roots are scanned for immutable
run snapshots. Scientific hashes and catalog artifact hashes are verified before
reading candidate identities. Only identities, former hypothesis status and
compositions are imported; historical predictions are not asserted to be current
measurements or scores. Missing history roots are allowed; existing corrupt or
inconsistent sources are reported, not silently ignored.

Previously recorded hypotheses have priority and mandatory follow-up within the
current supported domain. Earlier selected catalog pairs remain part of history.
New V5m-4.1 pairs are retained in the cumulative known-pair registry, including
pairs subsequently outside the current model/chemical scope. After a changed
scientific context, prior controlled hypotheses are retained for renewed study.
Historical out-of-scope identities are reported; scope guards are not bypassed.

The same basic suite runs for every pair. Detail selection is cumulative across
all completed pairs in the current scientific context, not the current batch
alone. It combines controlled merit, genuine two-model spread, a bounded number
of unresolved cases and mandatory historical hypotheses. Historical mandatory
work can exceed the ordinary detail/finalist budget; the selected count is visible.
Other expensive work remains explicitly budgeted.

## Common studies and controls

Every evaluated pair/stage receives:

- coverage of the requested formulations and model profile;
- failure diagnosis with original error messages and example conditions;
- same-binary-model zero-additive controls;
- evidence requirements with no fabricated values or sources;
- already-computed delivery requirements, without a fabricated pore model.

The HEOS mass score is preserved. A second column divides each model's candidate
mass by that same model's zero-additive mass, using the same profile and delivery
assumptions. This is not a shifted enthalpy or calibrated correction. Missing
zero-limit results remain missing and block a controlled gain hypothesis.

An exact-replay hypothesis requires complete available models and controls,
compliance with the configured refined-to-exact numerical tolerance, and the
configured mass-gain margin against both HEOS and the matched zero limit. Agreement
of these checks still does not certify actual coolant performance. No accuracy
or statistical-coverage guarantee is inferred from numerical convergence.

Failure categories distinguish reference blocks, modeled storage/outlet phases,
unsupported gas bridges, property/model domains, delivery limits, invalid caloric
windows, task failures and unclassified errors. Original details remain in the
dossier. Aggregated failed-model-state counts are not independent experiments;
a formulation can contribute to more than one cause across models or conditions.
A modeled phase rejection is not an empirical demonstration of infeasibility.

The evidence module routes recorded needs. It does not yet acquire external data
or run new chemical/transport solvers. Delivery requirements are inherited mass
flux, peak flow, pressure and pump-work estimates. The output explicitly marks
hardware feasibility, pore permeability and heat-transfer coefficients as unknown.

## Adding a study

A trusted local Python module can export a `STUDIES` dictionary of unique names
mapped to functions with signature `study(data, config) -> dict`. Add its module
name to `continuation.study_modules`. Existing required studies cannot be replaced.
These modules run trusted Python, not a sandbox. Do not load untrusted plugins.

`data` contains the current pair, stage, records, raw responses and controls.
The supplied configuration excludes catalog, execution, publication and
continuation policies; these are not scientific study settings. Other configuration
keys, including dedicated custom study settings, participate in the study task
signature. The module source is hashed. Declare additional file/data dependencies
in module-level `DEPENDENCY_FILES`; undeclared dependencies are outside the cache
contract. Study return values must be finite JSON objects. Failure stays explicit
and prevents claiming a complete required suite.

A new study is applied to old and new pairs on the next invocation. The tests
verify that adding a study does not itself call the old thermodynamic solver.

## Publish from the repository root

Review before committing:

```bash
cd /home/user/DEV/autonomous-materials-lab
git add -A -- experiments/mixture-campaign/mission-v5m41-results/
git diff --cached --stat -- experiments/mixture-campaign/mission-v5m41-results/
git commit --only -m "Add cumulative V5m-4.1 mission results" -- experiments/mixture-campaign/mission-v5m41-results/
git push origin HEAD
```

Do not add `.campaign-cache`, force-add ignored files or run `git clean -fdx`.
A paused batch is a valid partial publication, not a completed full-catalog claim.
Inspect `remaining_pair_count`, `catalog_screening_complete`, all coverage counts,
zero-control status and recorded model limitations before drawing conclusions.
