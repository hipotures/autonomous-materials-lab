# V5m-4: Broad known-mixture search on a shared entry load

## What changes

`python run_campaign.py` now runs the mission campaign. The old property-only
protocol is preserved byte-for-byte in `run_property_campaign.py` and remains
available through `python run_campaign.py --mode properties`. The original
`campaign.yaml`, results, numerical backends and property-task cache are retained.
The new default configuration is `mission-campaign.yaml`.

This revision changes the search domain and objective. It does not claim a
validated reactive, porous-flow or ablative thermal-protection simulation.

## Run

From the repository root, using the existing environment:

```bash
git pull --ff-only
source experiments/entry-evaluator/.venv/bin/activate
python -m unittest discover -s experiments/entry-evaluator/tests -p 'test_mission_campaign.py' -v
cd experiments/mixture-campaign
python run_campaign.py
```

The same command resumes compatible work. Do not delete `.campaign-cache`.
Use `--retry-failures` to retry failed tasks, or `--recompute` to force another
execution while preserving published snapshots. `--workers 8` changes parallelism.
`--limit-pairs 2` is an optional smoke subset and does not replace the full-run
`latest.json`. Results are written to `mission-v5m4-results`.

The old protocol has its original defaults:

```bash
python run_campaign.py --mode properties
```

No package installation, online crawl, API key, physical measurement or automatic
Git push is performed by these commands.

## Broad catalog, not membership in the NRTL table

The catalog enumerates the locally installed `chemicals` identity inventory
before checking mixture models. Exact CAS/SMILES/InChIKey checks are reused.
NRTL directed parameters and Dortmund subgroup interactions are assessed
independently. A complete Dortmund-only pair is retained as
`single_model_exploratory`, not rejected for missing NRTL parameters. A failed
available second model is not silently discarded to improve a score.

The default neutral C/H/O domain, molecular-weight limit and excluded motifs are
explicit in YAML. The present provider requires the pure additive to be liquid
at the storage temperature. Therefore salts, ionization, reactive solutions,
dissolved solids and particulate suspensions are outside this first mission
provider. Known identity does not establish procurement availability or safety.

All eligible identities and individual rejections are retained. The default
budget selects up to 500 eligible pairs using a stable hash, independent of
predicted performance, names and NRTL availability. The program reports the
actual inventory, eligible population, budget limitation and model coverage.
It does not promise that 500 supported pairs exist in a particular installation.
Set `catalog.maximum_pairs: null` for all eligible pairs.

Each selected pair receives 40 initial mass compositions: 10 logarithmic points
from 0.0001 to 0.01 and 31 linear points from 0.01 to 0.60, with the repeated
transition removed. Thus 500 selected pairs would mean 20,000 binary formulations,
not 20,000 independent chemical identities. This is not a ternary-mixture search.

## Mission and temperature semantics

The fixed-load profile reuses the existing entry evaluator's atmosphere,
trajectory integrator, heating correlations, forebody rings and wall controller.
The initial configuration comes from `../entry-evaluator/config.yaml` with
explicit overrides: flight-path angle -11 degrees and
`brandis_johnston_2014` heating. Default inlet velocity remains 15 km/s at 200 km.
The inherited wall setpoint/limit remain 1100/1200 K. The profile records actual
computed pressures, heat fluxes, wall temperatures and correlation-validity
fractions. These are model-scenario outputs, not measured flight data.

An unlimited heat-removal collector records the demand for every ring/time step,
including a zero-area stagnation probe. That probe adds no mass but can invalidate
local delivery. The trajectory has fixed vehicle mass, geometry and control for
all fluids. A failed or incomplete demand trajectory cannot be ranked.

The fluid storage state is 293.15 K at 101325 Pa. Its requested outlet temperature
is set by the wall/approach controller, with a default ceiling of 900 K. The
inherited outlet-pressure floor of 100 Pa is recorded. The hot external gas
and the wall are not assigned the coolant temperature. A 3000 K ablator surface
is not introduced as a fictitious liquid-state request or a fabricated boundary
condition. Ablation and reactive high-temperature gas coupling are not simulated.

The profile is a demand replay, not feedback from injection to aerodynamic heat
flux. It assumes the prescribed cooling can be supplied and checks candidate
thermodynamics/delivery against that demand afterwards. Failed candidates do not
inherit a successful mass score from the assumed wall-temperature history.

## Thermodynamic scope and gas branch

The previous bounded NRTL/Dortmund liquid models are reused. Liquid correlations
are selected over a fixed temperature envelope. Ideal-gas heat capacities must
cover both their reference temperature and the requested gas-temperature range.
Liquid vapor-pressure correlations are never extrapolated to 900 or 3000 K.

An out-of-liquid-domain gas request is supported only after a bounded flash has
found a fully vaporized state at a configured bridge temperature no higher than
the requested temperature and at the same or a higher pressure. The subsequent
ideal-gas continuation assumes fixed chemical species and no reentrant
condensation. The bridge and branch are stored for each result. This is an
explicit modeling approximation, not proof of chemical stability or phase
accuracy. Requests without a valid bridge or outside the pressure/temperature
scope remain unsupported. The default flash pressure ceiling is 2 MPa.

Storage must be a single liquid. Exit liquid-liquid splits are rejected. The
enthalpy difference uses the same overall mixture composition and the actual
storage and outlet pressures. A same-model pure-water difference is checked
against HEOS at the same endpoints with the unchanged 5% control tolerance.
This checks a limiting case; it does not validate mixture caloric predictions.
The published mass denominator is the HEOS water mission evaluated on the same
load and delivery assumptions.

## Automatic stages

1. All budget-selected pairs and all initial compositions receive a 24-node
   heat-preserving quadrature of the actual mission demands.
2. Up to 20 pairs are selected using mass merit and model disagreement, with up
   to three compositions per pair. Neighbors are refined by new composition
   midpoints using the same rule for every pair, not a named-additive exception.
3. These compositions receive a 96-node quadrature.
4. Up to 20 pair-diverse finalists receive every distinct T/P state of the full
   discrete demand history, followed by time-resolved reconstruction of peak
   mass flow. The refined-to-exact mass change is reported against a 2% numerical
   tolerance. It is not a statistical uncertainty or continuous-time guarantee.

Quadrature preserves total demanded heat and chooses actual sampled T/P states
as medoids; it does not invent thermodynamic values by interpolation. Coarse
coverage refers to representative bins, not all hidden states in those bins.
The exact finalist stage does not omit unsupported coordinates. An incomplete
mission yields `mass_kg: null`, with explicit failed heat and a diagnostic partial
mass. No renormalization rewards missing hot or high-pressure states.

The working-fluid mass is integrated from required heat divided by usable
enthalpy. Positive pump work is subtracted from wall heat uptake rather than
credited as free cooling. Required pressure follows the inherited fixed pressure
margin plus prescribed porous pressure loss. A real viscosity/permeability-based
porous-flow solution is not implemented. Optional mass-flux limits can be set;
null does not mean hardware delivery was validated. Hardware mass, composition
change by preferential evaporation, reactions with air and injection drag are
not included in the score.

## Cache, provenance and correction

The existing content-addressed Store is reused under distinct `mission.*` task
kinds. Catalog discovery, load profile, quadrature, model selection, each
composition/model/state batch and mass scoring have explicit dependencies.
Library identity and selected correlations participate in numerical keys.
A model correction invalidates its dependent states; a reporting change does not
require thermodynamic recomputation. The original property-only task keys are
not relabeled as mission calculations.

A repeated campaign writes a new immutable snapshot and a finalist-difference
report. The complete catalog and initial screening are evaluated under the
current protocol, including formerly rejected or unselected cases. Changing a
budget can bring new cases into later stages without manually picking mixtures.
The current workflow is deterministic under identical inputs and runtime.

## Publication

Snapshots contain small `summary.json` and `manifest.json`, gzip full data and
bounded text CSV shards. `publication-index.json` records compression hashes.
Important outputs include:

- `report-catalog-*.csv`: eligible identities and available models;
- `report-ranking-*.csv`: every screened formulation and stage;
- `report-finalists-*.csv`: full-profile mass estimates and qualification;
- `mission-profile.json.gz`: time/zone heat demands and trajectory metadata;
- `pair-*.json.gz`: numerical results, failed states and selected model metadata;
- `report-evidence-needs-*.csv`: unresolved physical/model/procurement evidence.

The evidence report lists needs; it does not claim online acquisition or physical
experiments. All results remain `rankable: false`, `experimental_winner: false`.
A lower mass is a fixed-load, frozen-species model hypothesis only.

From `experiments/mixture-campaign`:

```bash
git add -- mission-v5m4-results/
git diff --cached --stat -- mission-v5m4-results/
git commit --only -m "Add V5m-4 broad mission campaign results" -- mission-v5m4-results/
git push origin HEAD
```

The allowlist excludes cache, worker requests, logs and temporary publications.
Review staged filenames before committing; previously tracked files are not
removed automatically by `.gitignore`.

## Tests and source APIs

The suite includes synthetic end-to-end execution, full/incremental equality,
model invalidation without trajectory recomputation, missing-coverage rejection,
zero-area constraints, pump energy, mixture selection, gzip round trips and real
Git ignore behavior. Three optional integrations require the actual installed
thermodynamic/entry libraries; skipped integrations are not successful numerical
validation. One compares generated demand heat with the previous entry evaluator.

Relevant public API documentation:

- https://chemicals.readthedocs.io/chemicals.identifiers.html
- https://thermo.readthedocs.io/thermo.unifac.html
- https://thermo.readthedocs.io/thermo.phases.html
- https://coolprop.org/coolprop/HighLevelAPI.html

The implementations and assumptions of the existing project entry and mixture
backends remain additional dependencies, not independent physical evidence.
